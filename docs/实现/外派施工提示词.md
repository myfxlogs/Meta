## T1 部署通道手术（状态：待发｜吸收 0037-p2-p1、0040、0034-p1-p1、0038-p1-p1）

**病根**：`config/gateway.textproto` 的 `integrate_cmd`（36 行）只会快进合并
（`merge --ff-only`），分支与 master 一分叉即全线红；且不先验分支存在，报裸
pathspec 错。当日 6 票约 20 次部署全死于此。

**改法**：
1. `integrate_cmd` 重写三段（单条 shell、沿用 `$META_EXEC_REF`、仓库 /opt/meta）：
   ① `git rev-parse --verify "$META_EXEC_REF" || exit 92`（分支不存在=专码 92）
   ② `git merge-base --is-ancestor "$META_EXEC_REF" HEAD && exit 0`（已合入，幂等）
   ③ `git merge --no-ff "$META_EXEC_REF"`（真合；真冲突退出非零，回滚语义如旧）
2. `internal/gateway/exec.go`（约 171 行 merge_conflict 判读处）：按退出码区分
   「分支丢失(92)」与「真冲突」，事件 note 前缀 `REF_LOST:`/`CONFLICT:`；
   两类事件照发不静默。
3. 单测三条新路径（已合入幂等／分叉可合／分支丢失红）＋既有快进路径不回归。

**禁区**：不动 check/deploy/probe/rollback 四步；不改路由表语义。

## T13 部署闸克隆语义修正（状态：待发·急件｜D-81｜0034 两次检查红实证）

**病根**（`internal/gateway/exec.go` ensureDeployClone 297-315）：
1. **克隆存在即复用**：`os.Stat(dir)` 在→原样返回——克隆钉死在首次尝试的
   状态，后续 master 再合并（含修测试的修复）永不可见；
2. **检查步测错世界**：`clone + checkout <交付ref>`＝交付时旧世界——
   修复在兄弟票里的分家票（0034 的修在 0034-p1）结构性永远过不了自己
   的检查。

**改法**：ensureDeployClone 改「每 attempt 同步到主线顶」——已有目录→
`git fetch <repoURL> <default_branch> && git checkout -q <default_branch> &&
git reset --hard FETCH_HEAD && git clean -fdq`（防陈旧克隆＋防脏残留）；
无目录→clone 后同径同步。default_branch 取项目配置（勿硬编码 master）。
交付 ref 不再 checkout——检查/部署对象＝**并后主线**（integrate 已在主线
做完合并；幂等径照旧）。ref 仍作 integrate 输入不变。

**锚**：①同一票两次 attempt，第二次前 master 前进（新提交）→第二次
克隆可见新提交（log 实证）；②0034 型锚——兄弟票修复并入主线后本票
检查必绿（本仓现实即活锚：T12 已并，修后 0034 检查应绿）；③克隆内
`git status` 净（clean -fdq 实证）。

**禁区**：integrate/deploy/probe/rollback 四步命令本体不动；B1 锁不动；
不引入删除主线历史的操作（reset 只作用于克隆）。
