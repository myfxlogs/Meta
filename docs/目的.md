# 目的

> 业主钦定稿 2026-11-01。改动须业主令。

## 一句话

**一套无人值守的多 agent 协作开发公司：接到指定项目，独立完成开发与交付，业主只需与一个人对话。**

## 定位

| 层 | 是什么 | 地位 |
|---|---|---|
| 开发交付机 | 需求 → 设计 → 施工 → 审计 → 部署，全链自动 | **本体** |
| 运维哨兵 | 生产异常 → 定性 → 成票进入交付机 | 本体的进水口 |
| 公司治理 | 席位、预算、升报、可见性 | 本体的副产品，不是目的 |

前身 v1 三者并列齐头并进，撑死于复杂度。v2 以交付机为唯一主线，其余按需长出。

## 客户

**业主一人。** 唯一对话口=CEO 席（终端+飞书）。前端只读，不聊天。

业主要的两件事：
1. 说一句话 → 变成票 → 自动跑完 → 前端看到结果
2. 出事时先于任何渠道知道「谁在修、修到哪」

## 多项目

meta 与项目无关。每个项目在 meta 登记一份**项目配方**（仓库地址、检查命令、部署配方、项目自有纪律文档）。O 是第一个登记项目；O 仓现有规矩（AGENTS.md 角色/check 绿戳/worktree/经验库）是 **O 的配方**，不是 meta 的纪律。

## 管什么 / 不管什么

- **管**：把「决定」变成「已部署的码」的全过程，以及这一过程的席位、壳、预算、可见性。
- **不管**：项目的业务决策（如 O 启用哪个策略族、动不动钱径）。这些由业主经 CEO 裁，meta 只负责执行成票。

## 红线

1. 全无人：从需求到生产生效零人工闸（业主只在 CEO 对话面出现）
2. 禁周期任务 / 禁轮询 / 禁快照表——全链事件驱动；唯一允许的时钟是「随事件重置的一次性闹钟」（见事件模型）
3. meta 内部契约（接口/存储/事件）零 JSON，全 protobuf；外部工具（壳 CLI / webhook）的 JSON 止于适配层
4. 全链 gRPC 流，含浏览器（Connect 二进制模式）
5. 票只活在 DB，仓库不再承载任务状态

## 成功判据

- 业主发一句需求，不再说第二句，前端上出现「已部署」
- 任一壳失效，交付不中断，CEO 收到一条通知
- 任一席位死亡/卡死，业主无需发现——系统先发现并处置
- 新项目接入=登记一份配方，零改码
