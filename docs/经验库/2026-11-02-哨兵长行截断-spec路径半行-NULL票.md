**实证**：票 0037 设计席（run dfb680399d1754b4，2026-11-02）——
`META_ADMIN:create_ticket` 行长 ~130B，devin -p stdout 按块冲刷，行在
`|` 段内被腰斩；`scanFrameText` 对每个 `\n` 分段不做完整性判，半行照样
过 `CutPrefix`→`adminSentinel`→`SplitN` 得截断 `parts[3]`→`os.ReadFile`
静默失败→`Spec=nil` 帧发出→0037-p1 落 **NULL spec**（标题段在截点前完整，
票照立）。净 file 行后到，`pairDedup` 按原文配对——两行原文不同**不配
对**，file 行再发一帧→主键冲突静默拒。终局：一票 NULL spec 僵票，
`inject_failed`×2。

姊妹坑：`2026-11-02-哨兵spec文件须在宿主可读径.md`（彼坑＝文件在但分支未
并读不到；本坑＝文件宿主可读仍在，**流路径串本身被截**）。

## 打法

- **create_ticket/fill_spec 等含路径长行：先写 sentinel.log 再讲别的**——
  `pumpSentinelFile` 只取 `\n` 收口的完整行，文件径永不截断；stdout 流
  副本最后补发配对（截不截都已无妨）。**次序即防御**。
- 兜底确定性径（先例 0008/28）：`meta ticket new --spec-file`＋
  `meta dispatch`——CLI 进程内 ParseTicketMD+marshal 直送 AdminGateway，
  不过席位流。
- 诊断信号：票立了但 `spec IS NULL`＋`inject_failed`（缺一不派）——
  即本坑或宿主不可读坑。
- NULL spec 票无自救径（fill_spec 限本票；void 属 CEO）——立票前先验
  `spec IS NULL` 再放行是立票侧待补闸（已向 CEO 报债）。
